# Основа, изменения и причины

[English](../en/architecture.md)

## MCP как OAuth2-клиент AAS

Раньше MCP только проверял токены Keycloak, а его OAuth-клиентом был LiteLLM. По уточнённому требованию MCP переведён на **FastMCP OAuthProxy**: он сам является confidential client AAS, принимает `/auth/callback`, обменивает код с S256 PKCE и обновляет upstream-токены. Для LiteLLM MCP выступает отдельным сервером авторизации и выдаёт свои токены. Секрет AAS в LiteLLM больше не передаётся; прежний прямой клиент на стенде выключен.

Использован готовый OAuthProxy вместо самописной реализации протокола: consent/CSRF, state, PKCE, регистрация downstream-клиентов и привязка токенов остаются в библиотеке. Наш код задаёт строгие redirect URI, проверяет upstream JWT и сохраняет OAuth-состояние через FileTreeStore + Fernet. Нужны постоянные ключ и том, одна реплика. Старый режим доступен только явно: `OUTLOOK_AUTH_MODE=resource`.

Это не механизм извлечения пароля из OAuth2 и не доказательство входа пользовательским токеном в Exchange. EWS-адаптер по-прежнему использует служебную учётку. Доступ к реальному AAS определяется его контрактом.

## Что действительно использовали

- **[FastMCP](https://github.com/PrefectHQ/fastmcp):** регистрация инструментов, HTTP MCP, проверка JWT/JWKS и discovery защищённого ресурса. В проверенном lock — 3.4.11.
- **[exchangelib](https://github.com/ecederstrand/exchangelib):** модели данных EWS, операции с ящиком и NTLM-транспорт. В проверенном lock — 5.6.0. EWS/SOAP с нуля не писали.
- **Keycloak + PostgreSQL:** настоящий пользовательский OAuth2 в локальном стенде. **Существующий LiteLLM 1.96.0:** шлюз, хранение и обновление пользовательских токенов.

Прикладной код `src/outlook_mcp`, тесты и файлы развёртывания написаны самостоятельно. Использование библиотек и архитектурный референс не означают копирование чужого исходного кода.

## Какой готовый MCP рассматривали

Проверяли [ItayElizur/mcp-outlook, коммит 9faaedf](https://github.com/ItayElizur/mcp-outlook/tree/9faaedf7e1aab586bd24058a80055b777cb1efda). Сохранили **идею**: проверять пользователя на MCP, а к EWS обращаться отдельно через impersonation. Вместо форка выбрали независимую реализацию.

Выводы относятся к указанному коммиту, а не ко всем будущим версиям. В нём не нашли LICENSE и декларацию лицензии в pyproject; это стало одной из причин не копировать и не распространять его исходники.

| Референс / исходный вопрос | Что сделали у нас | Зачем |
|---|---|---|
| Static-режим без авторизации; JWT включается отдельно | Авторизация обязательна для всех методов MCP | Инструменты удалённого шлюза не должны открываться без токена |
| Проверка issuer, audience и подписи | Verifier FastMCP + обязательные `exp`, тип access token, `sub`, проверки `nbf`/`iat` | Отклонять бессрочные, будущие и ID tokens; криптографию оставить библиотеке |
| Ящик выбирается по настраиваемому email claim | Точный issuer и административное сопоставление `sub → SMTP` | Изменение email в профиле не должно давать чужой ящик |
| В инструментах нет проверки scope каждой операции | Шесть scopes с проверкой до обращения к backend | Разделить чтение, изменение и отправку |
| Отправка и создание событий доступны через MCP Apps | Обычные MCP-инструменты со структурированным результатом | Работа через LiteLLM без специального виджета |
| Черновик используется как данные UI | `save_draft` сохраняет неотправленный объект backend | Показанный текст нельзя путать с черновиком в Exchange |
| Исключения могут стать обычным словарём error | MCP `isError`, маскирование внутренних backend-ошибок | Шлюз различает успех/отказ; внутренние детали не уходят клиенту |
| Доступен параметр безвозвратного удаления | Перемещение в корзину; permanent delete не реализован | Сохранить возможность восстановления |
| EWS-схема по умолчанию Exchange2013 | Согласование версии средствами библиотеки | Не фиксировать произвольную схему; её имя само по себе не доказывает несовместимость с 2019 |
| В проверенном дереве нет контейнерных/Kubernetes-манифестов | Non-root образ, read-only FS, внешние secrets/config, stateless HTTP | Контейнерное развёртывание; OAuth proxy требует одну реплику и постоянное состояние |
| Тесты маршрутизации используют подставной token accessor | API-тесты и живой прогон Keycloak → LiteLLM → MCP | Проверить OAuth, пользовательский контекст и refresh между реальными компонентами |

`confirm=true` — условие API, **не независимое подтверждение человеком**. Клиент обязан получить реальное разрешение пользователя. При неопределённом результате EWS-отправки нельзя автоматически отправлять повторно.

## Что сознательно осталось за рамками

Реализованы 12 инструментов, а не весь Outlook. Ответ/пересылка с сохранением цепочки, редактирование черновиков, загрузка вложений, категории, free/busy, приглашения/ответы на встречи и делегированные общие ящики — последующие расширения.

Demo — небольшой синтетический backend в памяти, не эмулятор Exchange. Его поиск, адресная книга и календарь не доказывают поведение EWS. Совместимость с живым CU15, доставка, NTLM/Extended Protection и работа в Kubernetes ещё не подтверждены. Публичный код и успешные синтетические тесты не означают готовность к production.
